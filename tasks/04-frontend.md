# PHASE 4 — Production-quality hackathon frontend (approved scope)

## Mission and scope
Build a compelling product UI to make the **already existing and verified** RippleProof graph reasoning, supply disruption simulation, actual MCP traces, and persistent decisions visible to the Graph Hacks 2026 Track 1 judges. This is not a landing page or illustrative mockup. The UI must call the **real** FastAPI/FalkorDB backend.

Do **not** modify existing operational data, rename existing route contracts, replace the real simulation with fake outputs, or reset any Docker volume. Work within the existing project. Phase 5 and remote deployment are not authorized.

## Prioritized implementation plan

### P0 — Contract discovery and safety gate
- Before writing TS types, inspect the local OpenAPI JSON at `http://127.0.0.1:18000/openapi.json`, existing Pydantic models and actual sanitized JSON returned by the running API. Generate or hand-build types *from verified contracts*, not from an imagined schema. Add a contract smoke test.
- Preserve and document existing APIs; expected routes include `/health`, `/api/graph/summary`, `/api/impact-paths`, `/api/alternatives`, `/api/scenarios/simulate`, `/api/agent/run`, `/api/decisions/prepare`, `/api/decisions/approve`, `/api/decisions`, and `/api/decisions/{id}`. Verify exact methods, request fields and shapes from source; do not assume this list is exhaustive.
- Keep the already-verified `rippleproof` graph and all existing data/volumes untouched. Record initial physical and operational counts. No automated base seed or migration against live graph.
- Implement an HTTP client with validated request/response typing, AbortController cancellation, meaningful 401/404/409/422/503 states, and retries **only for safe read-only operations**. Handle oversized server results without rendering every nested record.
- Configure a same-origin Vite development proxy for `/api` and `/health` or a carefully limited backend CORS policy. Do not expose FalkorDB to browsers or put secrets in frontend environment variables.

### P0 — Real end-to-end user journey
1. **Overview / Command Center:** live backend health state; graph node/edge counts clearly separating operational and physical memory counts; meaningful explanation of the technology; current scenario summary if available; entry into scenario workbench. Never call graph health "healthy" based only on frontend state.
2. **Scenario Workbench:** supplier selector, `as_of`, start date, exclusive end date, mitigation toggle and chosen policy. Default fields may be prefilled with the verified *synthetic demo scenario* S-04, 2026-10-15, outage [2026-10-16, 2026-10-24), cost_first, but support user changes. Guard invalid windows with inline messages; calculate results by POST `/api/scenarios/simulate`. Explain that the end date is exclusive.
3. Show a three-column **Baseline → Disruption → Mitigation** comparison with on-time/at-risk counts derived from actual response, newly affected orders, restored orders, additional procurement cost, and clear source/assumption footnotes. Show genuine figures from the backend. The known seed can demonstrate 19 → 18 → 20 on-time orders and an additional gross synthetic cost of 1364.00; NEVER hardcode those numbers into production components or switch silently to fixture data.
4. **Material breakdown / alternative vendors:** selectable part, quantity demanded vs available, available alternative offers, dated capacity and certificates. Show **why** S-10 can be rejected for P-22 for missing C-02 while simultaneously valid for P-12 requiring C-01. A vendor is not globally "approved"; suitability is per part and arrival date. Unknown or missing evidence is labeled unknown, not valid.
5. **Evidence Graph:** focused, interactive and legible Cytoscape graph of the selected supplier → part ← product ← order evidence chain; preserve relationship directions and real edge IDs. Click nodes and edges to inspect original properties and source references. Filtering, reset/fit and keyboard alternative list required. Build the subgraph from **real evidence paths**; if the existing routes do not supply sufficient authoritative topology for a selected path, add *one narrowly scoped read-only backend projection* with a parameterized, bounded Cypher query and unit/integration tests. No raw Cypher from browser, no full-graph unbounded response. Default to scoped path view rather than 145+ visual items and noisy inbound receipts.
6. **Agent & MCP trace:** show the guided mode clearly as "Guided demonstration — 0 LLM calls" using actual `mode:guided` HTTP response and actual MCP tool_trace entries. Show ordered tools, statuses, timestamps, evidence, factual response, limitations and runtime errors. UI must NOT call it autonomous AI. If the genuine remote model provider is not configured/authorized, show `Real AI agent not configured` with no false badge or inferred call count. Handle `provider_not_authorized` (503) helpfully without changing provider settings or making any paid call. If provider is later activated by explicit operator authorization, display returned model_requests and actual tool traces as reported by backend, not simulated progress.
7. **Decision preview and decision ledger:** selected plan -> POST `/api/decisions/prepare` -> **read-only full review** (proposed amounts, quantities, arrival dates, total gross cost, all certification evidence, assumptions, scenario fingerprint/revision, expiry/staleness) -> optional explicit human approval. Approval must be separate from AI, never automatic, and **never a real purchase**. Display saved decisions from actual GET endpoints, scenario/history filtering, detail, related evidence, and correct empty state (the live graph may initially have none).

### Approval safety requirements — local single-user demo only
- The existing `RIPPLEPROOF_APPROVAL_SECRET` is backend-side. Never inject it into Vite variables, generated JS, localStorage, sessionStorage, the URL, remote logs, or a model tool. Never silently auto-confirm.
- For a local-only UI, an operator may **manually paste** their already-configured secret into a transient password field in an explicit review dialog on trusted localhost. Keep it in volatile component memory **only for the attempt**, clear after request/dialog close/navigation, prevent logging, and require typed confirmation `APPROVE INTERNAL`. Do not transmit it to LLM or MCP. Clearly label this as local demo authorization, not production authentication. A server-side authenticated operator gateway is preferable only if it can be implemented correctly within scope.
- If the app is accessible from any non-loopback origin and no proper authenticated server-side gateway exists, **disable browser-side approval entirely**; keep preview and history visible and direct operator to the documented CLI flow. Do not pretend the UI has an approval feature in that mode.
- On `409` stale preview, discard all approval inputs, reload source-derived preview, and force fresh manual review. On `401`, present an authorization message without echoing the token. On `422`, show safe validation messages. On `503`, show approval unavailable. Idempotency key must remain constant for a network retry of **the exact same intended action**, never reused for a modified action.
- In a successful localhost human demo, check the newly persisted decision in the Ledger and verify scenario ID / operational fingerprint stay identical. Approval persists an **internal decision**, not procurement or reservations. Preserve backend's one-worker/serialized external-writers limitation; do not claim cross-writer transactional guarantees.

### P0 — Technical UI architecture
- New `/frontend` package: React, TypeScript in strict mode, Vite, typed API service, TanStack Query or equivalent disciplined server-state caching, Cytoscape.js, Lucide icons, modular accessible UI components and CSS tokens. Avoid large UI frameworks that create unmaintainable autogenerated screens.
- Organize by features (`overview`, `scenarios`, `evidence`, `agent`, `decisions`) with small components and robust state boundaries. URL/shareable filters are okay **only without secrets**, and should not imply replay of outdated previews.
- Provide a `frontend` Compose service or clearly documented Vite dev/prod setup. Prefer localhost ports `127.0.0.1:18080` for web (if available) and existing `127.0.0.1:18000` for API. Do not change the existing backend/data exposure or volumes. Preserve existing compose defaults, health checks and test-profile behavior.
- Avoid long-running server errors through clear loading, cancel, retry (safe requests only), empty, partial-evidence and disconnected states. Backend 503 means **service unavailable**, never fall back to fictional fixtures.
- A full simulation may be ~0.9 MB: derive small view models once from the validated payload, use tables with pagination/virtualization where appropriate, never render whole JSON by default. Only explicitly view raw data in a collapsible developer inspector.
- Respect reduced motion, focus-visible, interactive keyboard graph alternatives, sufficient contrast, descriptive controls, accessible errors and responsive layouts at ~1440, 1024, 768, 390px. Never rely on red/green color alone for status.
- Adopt the domain-specific visual direction in `docs/PHASE4_UI_DESIGN.md` consistently across all screens. Do not use emojis or generated placeholder illustrations.

### P1 — Optional if P0 is complete

## Definition of done / verification gates
- UI is responsive, polished, coherent and usable (English-first for international judges); no emojis, broken Turkish glyphs, decorative dashboards or lorem ipsum.
- Every displayed status, number, path, price and certificate has a real API source. Guided mode is honestly labeled; `mode:agent` unavailable is handled truthfully.
- Freshly loaded demo works against real backend: inspect S-04 impact, simulate, compare three states, inspect per-part certification, traverse evidence path, execute guided MCP trace, prepare decision, list history and (if locally authorized) manually approve and retrieve the persisted record.
- Verify new frontend tests plus at least one **real-backend browser end-to-end run**; mocks allowed in separate component/failure-state tests and must be labeled in reports. Browser test should cover frontend network behavior and console errors.
- Test failure states: empty graph or unknown IDs; invalid date; DB unavailable; provider not authorized; missing approval secret; 401/409/422/503; evidence pagination; backend restart. Do not mutate live source data to test staleness: use isolated graph/test harness.
- Existing 166 Python tests must still pass, including actual FalkorDB integration cases. Pass Python lint and Compose checks; pass TS typecheck, lint, production build, meaningful UI tests and real-browser E2E.
- Record screenshots at desktop/tablet/mobile; note any accessibility findings, app startup commands, real browser output and precise test count; don't claim a real provider call if none happened. Create `docs/PHASE4_VERIFICATION.md` and a concise `docs/DEMO_PHASE4.md`.
- Report files changed, API additions, tests and failures, known security limits, and operator steps. STOP before Phase 5.
